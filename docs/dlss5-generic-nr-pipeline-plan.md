# 通用 DLSS 5 NR 多次推理与 Look 调整实现计划

日期：2026-10-04  
状态：实施中；P0/P2/P3/P4/P5 代码已落地，双实例与时间 Look 的隔离 GPU 验证通过，真实视频、组合交接与性能验收待完成  
目标环境：Windows、Eden / Citron 等 Switch 模拟器，优先验证 Vulkan 输出路径

## 1. 目标与实施边界

在已能运行一次 Neural Rendering（NR）的接入层上，增加两类可复用能力：

1. 多次 NR 推理：多个独立实例串联，每个实例分别维护时序历史和参数。
2. Look 调整：控制模型带来的明暗、颜色、色相、整体光照与细节变化，随后增加光晕抑制和可选的时间平滑。

算法与游戏识别解耦。不同游戏主要保存参数预设，不为每个游戏重写推理调度和 Look shader。

本计划不包含重新训练或修改 NVIDIA 模型权重，不把通用光流当作游戏原生运动矢量，也不承诺解决所有模型产生的细节或人物外观变化。

计划起草时本地读取工具启动失败；首轮实施现已核验本仓库已有 `streamline-fg/native-nr` 管线。实际落点、数据契约、验证和剩余限制见 [首轮实施记录](dlss5-generic-nr-pipeline-implementation.md)。下面的概念接口仍不能自动视作仓库已有能力。

### 工程落点

| 层 | 职责 | 实施原则 |
| --- | --- | --- |
| 本仓库 Rust 侧（`src-tauri`） | 能力探测、配置校验、预设、组件版本记录、启停和诊断结果 | 优先沿用已有结构；不让普通配置代码承担每帧 GPU 工作 |
| NR 运行组件 / add-on | GPU 资源接入、NR 实例调度、Look shader、历史和同步 | 先验证已有组件能否直接满足需求，再决定是否维护独立组件 |
| 模拟器渲染后端 | 在需要原生深度或运动资源时提供准确的纹理和时序 | 通用方案首版不要求修改 Eden / Citron 源码 |

本次只新增计划文档。后续本仓库代码默认在 `src-tauri` 实施；需要新增或修改独立运行组件、shader 或模拟器源码时，先明确实际目标仓库与实施范围。

## 2. 已确认的参考能力与待核验条件

公开的 RenoDX NR 源码中已有独立 NR handle 串联、每实例历史重置和外部 Look stage。其四遍上限属于插件实现，不是本计划必须照搬的限制。

公开的 Eden / Citron 渲染代码有定位深度纹理的机制，但“存在深度资源”不等于已经找到与当前显示画面匹配的主场景深度。原生运动矢量还需要识别游戏是否生成、存放位置、编码和对应帧。

DLSS5-Feeder 提供 Vulkan 到 D3D12 的接入路线，读取 ReShade 深度及外部光流 shader 输出。这是首轮实验的候选方案，不能据此认定具体模拟器、游戏、显卡或插件版本已经验证通过。

开始实施前记录：

- 当前工程是否已有可复现的一遍 NR 输出，实际使用哪个运行组件。
- 模拟器、ReShade、feeder、NR add-on、驱动、模型 DLL 的具体版本与文件哈希。
- 显卡、图形 API、NR 输入尺寸、模拟器内部渲染尺寸和最终输出尺寸。
- 深度、运动矢量的来源与质量；区分原生、估算、占位和缺失。
- 当前运行组件能否暴露逐遍参数及 Look 参数，是否需要自行实现 GPU 处理。

## 3. 通用管线

```text
模拟器颜色 / 可用引导资源
          │
          ▼
接入适配器：尺寸、颜色空间、坐标和 GPU 同步
          │
          ▼
NR 调度器：实例 A → 可选实例 B → 后续可选实例
          │                    │
          │                 各自历史
          ▼
Look stage：变化量控制 → 可选空间处理 → 可选时序处理
          │
          ▼
沿用接入层的 SDR / HDR 合成与输出
```

首版 Look 位于最后一遍 NR 之后，保留最后一遍实际输入和输出作为变化量计算依据。首版不增加“每一遍都执行 Look”或“相对整条链原始输入调整”的额外语义。

### 数据契约

帧输入至少包含：

- `source_frame_id`：源渲染帧编号；与呈现编号、插帧编号分开。
- 颜色纹理、格式、尺寸、有效区域和生命周期。
- 颜色空间、传递函数，以及 HDR 时接入层已有的曝光 / 单位契约。
- 可选深度和运动纹理，以及各自尺寸、有效区域和坐标约定。
- 运动方向、单位、缩放、是否含 jitter，以及质量标记。
- 场景切换、分辨率变化和设备重建等重置信号。
- 所属 GPU / device、提交队列及完成同步信息。

深度与运动质量是显式能力，不用一张全零纹理冒充有效数据。若运行时需要占位资源，必须在能力和诊断中标记其实际性质。

同一源帧只推进一次每个实例的历史。若接入层只能看到 Present，必须先核实重复呈现、暂停和插帧的识别方式；不能直接把每次 Present 都当作新的游戏帧。

## 4. 多次 NR 推理

### 首版功能

- 支持一遍和两遍；默认一遍。更高遍数在性能和稳定性验证之后再开放。
- 每遍独立持有 NR handle、参数块和历史重置状态。
- 第一遍读取接入层的颜色；第二遍读取第一遍按既有 codec 正确处理后的输出。
- 引导资源来自同一源帧；不能随意缩放、改变运动单位或混用不同帧的数据。
- 中间纹理采用 ping-pong，保证输出不会覆盖尚在读取的输入。
- 所有纹理处理留在 GPU；首版不设计逐帧 CPU 图像读回。

### 参数与历史

- 每遍可配置强度，以及经实际运行组件确认支持的模型参数。
- 默认第二遍继承第一遍参数；只有关闭继承时才使用第二遍独立设置。
- 场景切换、实际尺寸变化和输入解释变化时协调重置所有相关实例。
- 改变模型实例创建契约时重建实例；普通 Look 滑块不重建 NR 实例。
- 每遍历史是否保留须明确配置和日志；不能默默让第二遍每帧 Reset。
- 减少遍数或关闭 NR 时，等待对应 GPU 提交完成后释放实例和纹理。

### 失败行为

第二遍创建或执行失败时，输出已完成的第一遍，并记录失败原因。失败状态必须有重试策略或显式恢复入口，避免每帧重复创建造成卡顿。

## 5. Look stage

### P2：基础变化量控制

保留模型实际输入 `P` 和输出 `N`，在一致的分辨率及线性颜色空间中计算变化量。参考形式为：

```text
e = log2(max(N, epsilon)) - log2(max(P, epsilon))
```

调整后的变化量用于生成新的模型输出，再进入原有输出合成。实现需明确暗部可信度保护；不能只靠除零下限就放大接近黑色区域的数值误差。

第一批参数：

- 整体增强幅度。
- 提亮、压暗的独立增益和软上限。
- 颜色变化和色相偏移的独立增益。
- 阴影、中间调、高光区域的变化量控制。

中性参数必须保留 NR 原输出。允许完全绕过 Look dispatch，避免多余转换改变 SDR / HDR 结果。NR 关闭时也应绕过整个新增管线。

不能直接把原始 HDR 颜色和经过压缩、归一化的 SDR 模型输出相除。Look 必须遵守当前接入层的输入 / 输出 codec 契约，避免重复 tone mapping 或错误曝光还原。

### P3：空间处理

- 以输入亮度为引导，对亮度变化量做空间分离。
- 独立调整大范围光照变化与细小变化。
- 对满足邻域条件的边缘压暗变化执行光晕抑制。
- 半径按 NR 工作分辨率解释，避免输出分辨率变化后效果尺度失控。
- 验证平坦表面、真实阴影、文字边缘和大反差轮廓，避免新增亮框或破坏原有阴影。

基础空间处理只依赖当前帧颜色及 NR 输入 / 输出，不要求游戏原生运动矢量。

### P5：可选时间平滑

- 保存上一源帧的模型变化量，而不是直接累积整张最终画面。
- 优先使用已经验证的运动资源；通用方案可使用光流估算。
- 重投影后进行邻域限制、置信度判断和历史拒绝。
- 平滑时间以毫秒表达，按实际帧间隔计算混合系数。
- 遮挡、视角切换、暂停恢复、较大时间间隔及尺寸变化时拒绝或重置历史。
- 输入质量不足时减少历史混合；没有可信运动资源时默认关闭运动补偿平滑。
- Look 的历史与 NR 内部历史分别管理，不能为了调整 Look 而每帧重置模型。

该阶段不阻塞基础 Look 或两遍推理。它依赖运动数据质量，必须单独验收，不能靠静态截图判断效果。

## 6. 配置、预设与诊断

### 配置语义

- 配置包含 schema 版本、遍数、逐遍参数、Look 参数和时序策略。
- 默认 NR 沿用既有开关；新增多遍默认为一遍，Look 默认为中性，平滑默认关闭。
- 参数与实际后端能力匹配，不支持的参数明确报告，避免显示已启用却没有效果。
- 预设按模拟器、游戏和必要的显示模式区分，保存运行组件版本以便复现。
- 导入配置时校验有限浮点数、数值范围和枚举；迁移保持已明确选择的参数。
- 恢复默认与绕过新增功能是独立且可验证的操作。

### 诊断信息

- 当前模拟器、接入路径、运行组件及模型文件版本 / 哈希。
- 颜色、深度、运动矢量的来源、尺寸和可信状态。
- 当前执行遍数、每遍是否成功、是否重置历史以及原因。
- 各阶段 GPU 耗时：接入 / 拷贝、逐遍 NR、Look、输出。
- 活跃实例与纹理数量、显存占用，以及等待释放的资源数量。
- 能力不足、失败降级和不支持参数的明确原因。

渲染组件内部调试可提供颜色、深度、运动、变化量和历史权重视图。普通用户配置界面只展示有助于选择和排错的信息。

## 7. 实施顺序与阶段验收

| 阶段 | 工作 | 验收条件 |
| --- | --- | --- |
| P0：工程与接入调研 | 阅读本地说明和代码；确认运行组件；固定测试组合；核实许可证与参考代码版本 | 给出真实工程落点和已支持能力，不把候选方案记为已完成 |
| P1：一遍基线 | 跑通当前接入；确认颜色契约、源帧节奏、同步和重置 | 开关效果可见；旁路输出保持原路径；连续运行和窗口切换稳定 |
| P2：基础 Look | 实现变化量、明暗 / 颜色控制及中性绕过；接入 Rust 配置和诊断 | 中性保持 NR 输出；暗部无 NaN / 闪点；明暗和颜色限制有可复现效果 |
| P3：空间 Look | 大范围 / 细节分离及光晕抑制 | 对照视频中边缘问题改善；平坦区域、文字和真实阴影不出现明显新增伪影 |
| P4：两遍推理 | 独立实例、历史、ping-pong、参数继承和失败降级 | 第二遍生效；每个源帧只推进一次各实例历史；降级稳定且资源可回收 |
| P5：时序 Look | 光流或已有运动资源接入、重投影、置信度和历史拒绝 | 慢速平移闪烁减少；快速转向、遮挡和切场景没有不可接受的拖影 |
| P6：预设与集成 | 保存 / 导入 / 迁移预设，能力提示，完整回归 | Eden / Citron 分别有实际测试记录；预设可复现；不支持组合有明确状态 |

首个可交付版本为 P0–P2。空间处理、多次推理和时间平滑分别推进，避免把所有功能绑成一次大改动。

## 8. 验证方案

### 正确性

- 使用固定输入检查中性 Look、完全绕过、零变化量和极暗 / 极亮区域。
- 检查 SDR 与实际支持的 HDR 契约，确认无重复转换、黑位漂移和非有限值。
- 用真实运动序列检查方向、单位、有效区域、动态分辨率及历史重置。
- 在原画、一遍 NR、一遍加 Look、两遍 NR、两遍加 Look之间做独立对照。
- 保留输入帧、参数、版本信息和输出；不能仅凭不同场景的截图判定算法收益。

### 游戏场景

至少选用一个 Eden 和一个 Citron 的实际测试组合，覆盖写实风格与卡通 / 风格化画面。场景包含：

- 暗处进入亮处、光照闪烁和高反差轮廓。
- 慢速平移、快速转向、遮挡与显露。
- HUD、字幕、透明物体、粒子和细小植被。
- 暂停、读档、切场景、窗口 / 全屏切换及分辨率改变。

原生深度、估算运动和占位资源等组合分开记录；不把原生 DLSS PC 游戏的经验直接写成模拟器验证结果。

### 性能与资源

- 固定硬件、驱动、版本、分辨率、输入质量和场景。
- 分别记录源帧帧时间、各阶段 GPU 耗时、显存、CPU 开销和长帧。
- 分开统计预热 / 创建开销与稳定运行开销，不用插帧后的 FPS 代替 NR 耗时。
- 循环切换遍数、开关和分辨率，验证实例与纹理数量最终回落，不持续增长。
- 依据实测决定是否开放更多遍数、低分辨率 Look 或更强的平滑，而不预先承诺性能提升。

后续若修改 Rust，按仓库要求执行 `cargo fmt`、host 与 Windows target 的 `cargo check`，并解决出现的错误和警告。GPU 运行组件使用其自己的构建、shader 编译和实机验证流程。

# NR 时序历史修复与串联性能复测（2026-10-01）

**已修复固定模拟器中物理源纹理与呈现对象正常轮换导致的逐帧 NR reset。NR → DLAA 在当前场景的 20 多 FPS 尚未修复，P1/P2 也未通过。** 完整统计、运行库身份、控制应用记录和原始文件摘要见 [summary.json](summary.json)。此前的 [P1](../nr-p1-2026-10-01/README.md) 与 [性能对照](../nr-perf-2026-10-01/README.md) 保留为历史记录。

## 身份与生命周期

NR 原先以物理源图像句柄判断来源。模拟器正常交替使用两张源纹理，因此每帧都被判为 `SourceChanged`。第一版逻辑源组虽允许纹理轮换，却还要求同一个 pipeline/render pass 句柄；实机仍逐帧 reset。新诊断确认同一画面会轮换三个 render pass，加载与游戏阶段还出现两条识别通过的 pipeline，共六组路径组合。这轮两个源分配的创建代次、尺寸、格式、映射和 usage 均稳定。

修正版为每个 device/queue/swapchain 保存有界的已观察成员：最多八张源纹理、八组已识别呈现路径。首次遇到成员时递增历史 epoch，重置一次；已知、存活且契约一致的成员轮换时保持 epoch。逻辑契约包含源尺寸、格式、采样/层级、crop/flip、viewport 和 framebuffer 尺寸。不同源分配的附加 usage 位不作为颜色来源变化；每个分配完整的 usage 与创建代次仍保存在生命周期快照中。

每帧仍先要求唯一的识别绘制、匹配的提交/呈现 semaphore、正确的提交位置、源同步、通道结束与呈现布局转换。绘制后的图像或 pipeline/render pass 创建代次变化直接拒绝该源。组内任一已知分配或路径退休会切断历史，即使本帧没有使用那个成员；交换链销毁、缺失/歧义证据、关闭逐帧观察及组容量溢出同样不能沿用旧 epoch。这是固定构建的已识别呈现路径策略，不是对任意同尺寸图像自动认定来源相同。

NR 历史仍包含强度、映射、尺寸、帧连续性与运动可用性；NR、SR、FG 的待重置信号各自确认消费。NVOF 继续分析未经 NR/SR 处理的真实呈现帧对，并保留已有的 500 ms 中断保护。记录新增物理句柄、创建代次、逻辑 epoch、组成员数、路径及更新原因；验收器核对不重置帧的契约连续性、分配代次和提交给 NR 的实际 reset 参数，不将日志一致性等同于时序画质验收。

## 实机结果

运行库 A、调用桥、Streamline 2.12.0、固定模拟器和 RTX 5070 Ti Laptop / 610.88 沿用前次实验。源为 1920×1080，窗口交换链为 2560×1335，NR 强度 1，实际 FG 关闭，使用合成深度。修正版层 DLL SHA256 为 `a33a9c70b0e521939bd0ff09684052b3daade9f1832d2d0433bccc38c960c5be`。

| 会话（位于 `src-tauri/target`） | NR 评估 | 不重置评估 | 最长连续不重置 | NR → DLAA 交接 | 结果 |
| --- | ---: | ---: | ---: | ---: | --- |
| `nr-history-validation-001` | 3,304 | 0 | 0 | 0 | 首版失败，逐帧 `SourceChanged`，原始日志保留 |
| `nr-history-validation-002` | 3,244 | 3,219 | 1,178 | 1,432 | 修正版时序及交接一致，严格验证失败 |
| `nr-history-performance-001` | 12,225 | 12,214 | 7,419 | 9,968 | 无验证层/回读，调用链完成；不具备严格验收证据 |

修正版严格会话分别覆盖 NR-only 与 NR → DLAA 至少 300 帧连续不重置，全部评估的提交 fence 完成。NR 关闭时 SR 读取 `native_source`，恢复时读取本帧 `nr_output`；强度变化出现 `StrengthChanged`，之后恢复 `Continuous`。15 次读回均有限且无哨兵残留。强度 0 的三次输出与输入完全一致；0.5 和游戏中的 1 均有非零差异。首次三个强度 1 样本来自加载阶段，不作为游戏画质证据。

用户反馈修正版运动画面正常，手动暂停并恢复后画面正常。日志也记录运动不可用时停止 NR、恢复时 reset；加载/回读等情况同样会引起中断，不能将每条日志唯一归于用户手动暂停。暂停反馈不替代系统的暂停/最小化/resize 验收。

三个进程均先应用 NR/SR 关闭控制，再正常关闭，退出码为 0，NR 与共享 SDK 清理完整。这不证明此前的 managed WaitHandle 退出异常已修复。修正版严格会话仍有 **245 条验证错误、30 条未核查警告**，包括命令缓冲状态、图像布局、使用中资源销毁、查询状态和 shader 限制。消息中没有名称含 `dlssnr` 的对象，不据此排除未命名 NR 资源问题，也不把其他错误全部归于模拟器。所有错误照常进入失败报告。

## 当前场景的 20 多 FPS

用户在无验证层窗口反馈帧率只有 20 多 FPS，确认画面正常并保持当前地点/视角。完成六个约 30 秒的开关区间，应用控制后等待三秒再采样；区间均无回读，实际 FG 关闭，源跟踪与 CPU/GPU 计时保持开启。进程模块清单确认未加载 Khronos validation。

| 当前场景模式 | 完整帧数 | 平均帧间隔对应 FPS | 帧间隔中位数对应 FPS | Present hook 中位耗时 |
| --- | ---: | ---: | ---: | ---: |
| NR → DLAA，第 1 次 | 696 | 23.00 | 20.17 | 14.53 ms |
| NR-only | 852 | 28.15 | 29.94 | 11.37 ms |
| 全部关闭，跟踪保留 | 908 | 29.99 | 30.01 | 0.71 ms |
| NR → DLAA，第 2 次 | 773 | 25.58 | 29.66 | 14.49 ms |
| DLAA-only | 907 | 30.00 | 30.00 | 5.84 ms |
| NR → DLAA，第 3 次 | 712 | 23.55 | 20.99 | 14.70 ms |

平均 FPS 使用完整帧间隔均值的倒数，避免中位数掩盖 33/50 ms 等区间的混合；不是显示器扫描率。前次性能会话的场景不构成本轮严格回放对照，因此不以其 30 FPS 证明这轮串联应当达到 30 FPS。

第 1 次串联的 NR GPU Evaluate 中位约 8.03 ms，DLAA Evaluate 约 2.65 ms。NR 提交后等待自己的 fence，SR 提交后也等待自己的 fence；NR 等待还包含上游 NVOF。串联 hook 约 14.5 ms。第 1 次 hook 外中位约 34.3 ms，第 2 次约 19.5 ms，显示额外的游戏执行/呈现调度波动。当前数据定位到串联开启时的帧预算压力，尚未证明是哪一个等待或调度点导致全部差异。采样时没有逐帧历史重置、尺寸变化或重复资源重建，Reflex 与实验 sleep 限帧参数均为 0。

因此不能再将当前 20 多 FPS 归因于验证层，也不能声称本次已修复串联性能。下一步应补充整个帧的 CPU/GPU 排队与等待证据，再评估将 NR/SR 工作合并提交、延后 CPU 等待等方案；每种变更仍需证明输出就绪、输入生命周期与退休顺序，不能直接删除 fence。

## 检查与复测

`cargo fmt`、crate 的宿主与显式 Windows MSVC all-features/all-targets `cargo check`、SDK-only/默认透明层检查，以及主应用宿主/Windows 检查均无错误或警告。113 个测试通过，1 个硬件测试保持 ignored；新增回归覆盖双/三纹理轮换、呈现路径轮换、未选中成员退休、句柄代次复用、映射/编码变化、证据缺失、交换链退休、组容量边界及伪造连续日志。

Release 构建使用 `--features native-nr --lib --bin streamline-layer-probe`。严格会话按 [P1 启动参数](../nr-p1-2026-10-01/README.md) 使用固定 VVL、`--nr-readback --sr-mode dlaa --sr-scale 100`，再以原子 `control.json` 切换 NR-only、串联、开关与强度。性能会话去掉验证/回读参数，显式使用 `--nr-performance`。原始日志、PPM、控制与分析辅助脚本保留在 ignored `src-tauri/target` 下，不更改旧失败日志。

`execution_verified` 只说明严格会话中的 NR 输出与交接证据；`temporal_history.valid` 只核对记录一致性，需同时查看不重置长度。无验证层会话仅有 `call_chain_completed`，其 `execution_verified` 为 false。三个会话的 `session_verified`、`p1_passed`、`p2_passed`、正式性能和画质验收均为 false。安装与 GUI 仍不默认启用该实验。

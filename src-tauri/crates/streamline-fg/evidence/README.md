# Retained validation evidence

The [toolbox integration record](nr-toolbox-2026-10-01/README.md) covers local NR import, private package deployment, normal launches without diagnostic validation/readback, acknowledged strength and SR/FG controls, and DLAA startup without an NR model. It retains the failed SR acknowledgement run and the successful corrected run. Background FG requests are not counted as actual FG execution; this is experimental toolbox integration, not strict game acceptance.

The repository keeps only the five recorded fixtures used by `include_str!` regression tests and the compact final game measurements under `ryujinx-fg-2026-09-25`. Bulk per-frame logs, repeated experiment runs, machine snapshots and screenshots are disposable and are excluded from source control.

The compact [native NR P0 investigation](nr-p0-2026-09-30/README.md) retains runtime identities, output controls and the original validation failures. Its [coexistence/history follow-up](nr-p0-2026-09-30/coexistence-history.md) accepts the exact experimental P0 combination after NR/SR repairs, live-feature coexistence, shutdown ownership, resize and missing-motion tests. It does not establish simulator integration, NR-to-SR color flow or FG coexistence. Original logs and image readbacks remain in the ignored `target` sessions named in its summaries.

Historical experiment documents may name session paths that are no longer retained. They record past investigations, not a claim that those full logs ship with the source. The retained `live-control.json` records the observed on/off/on presentation rates and the subsequent window-operation stop. These CPU-side counts do not prove display scanout or visual quality. Experimental block-matching motion estimation remains opt-in and off in toolbox launches.

The [native NR emulator integration](nr-p1-2026-10-01/README.md) records actual NR-only and NR-to-DLAA execution, motion-scene readbacks, independent controls and the failed validation/exit gates. P1/P2 remain unaccepted: emulator validation errors, per-frame source resets and a managed shutdown exception still require investigation. The opt-in experiment is not enabled by the installer or GUI.

The [native NR performance comparison](nr-perf-2026-10-01/README.md) records eight same-view CPU/GPU timing phases. Disabling core/synchronization validation raises NR-to-DLAA from about 7 FPS to the current 30 FPS baseline. The explicit performance mode retains real synchronization and records validation as disabled; it cannot pass strict NR acceptance.

The [NR temporal history follow-up](nr-history-2026-10-01/README.md) repairs resets caused by live source-image and recognized presentation-object rotation, while retaining allocation generations and retirement checks. It preserves the unsuccessful first prototype, continuous NR/DLAA execution, strength readbacks and subsequent low-FPS measurements. Strict validation and general visual-quality acceptance remain unresolved; the earlier 30 FPS observation does not establish NR-to-DLAA performance in every scene.

The [NR GPU handoff experiment](nr-handoff-2026-10-01/README.md) replaces the intermediate NR CPU wait with an explicit semaphore consumed by SR, retaining the final SR fence. It records strict-validation failures and a same-build CPU-wait versus GPU-handoff performance comparison. Reduced intermediate waiting alone does not prove higher frame rate or formal acceptance.

The [deferred NR/SR tail experiment](nr-tail-2026-10-01/README.md) fences the copy of borrowed game inputs, then allows private NR/SR work and native presentation retirement to finish after returning to the emulator. It bounds pending work to one slot and drains before reuse, control changes and teardown. This remains an opt-in experiment with unresolved strict validation.

The [NR safety and readback follow-up](nr-safety-2026-10-01/README.md) serializes native device queue calls, adapts layouts only for proven SDK-created proxy images, and uses cached host readback analysis. The final resize test removes seconds-long readback stalls; application resource-lifetime and other strict validation errors remain unresolved. It retains the unsuccessful half-conversion-only experiment and all four final session summaries.

The [NR/SR/FG eight-combination test](nr-combinations-2026-10-01/README.md) records actual foreground FG, per-frame color flow and reset propagation while unchanged SR/FG consumers remain active. All eight runtime combinations were observed with normal moving-picture feedback and clean retirement. Two SDK FG clone initial-layout errors are retained separately from known emulator errors; safe-failure and formal quality acceptance remain incomplete.

The [SDK FG initial-layout investigation](sdk-fg-layout-2026-10-01/README.md) reproduces those two errors without NR or an emulator, captures the incorrect first barrier, and verifies the Rust adapter with the same DLL in off/on sessions. Both initial-layout errors disappear while actual FG and retirement continue. Independent SDK/NGX transfer synchronization errors remain strictly recorded; the sessions do not pass zero-error acceptance.

The [SDK FG transfer synchronization follow-up](sdk-fg-transfer-2026-10-01/README.md) completes existing shader-only image and buffer barriers for SDK-owned NGX transfer operations. Its same-build SDK-only comparison reproduces 20 reported errors with the adapter disabled and passes core/synchronization validation with zero errors and warnings when enabled. Earlier failed and foreground-timeout runs remain recorded; SDK textual warnings and emulator errors are not reclassified as Vulkan validation passes.

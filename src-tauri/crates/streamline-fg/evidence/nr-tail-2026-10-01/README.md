# NR/SR 链尾等待与 Present 回收延后（2026-10-01）

实现了一帧有界的延后回收。`NS_STREAMLINE_DEFER_PRESENT=1` 在实际 FG 关闭、SDK 没有待消费 FG timeline、已识别原生源且本帧不读回时启用；未设置或为 `0` 保持上一轮 NR → SR GPU 交接、SR 链尾 CPU 等待的路径。安装与 GUI 仍不默认开启原生 NR 实验。

## 资源与同步

不能把模拟器借出的源纹理直接留到返回之后使用。本实现把 NR 输入准备拆成独立 command buffer：等待 NVOF 完成，复制颜色、运动至私有资源，恢复源布局，等待 input fence。此时模拟器输入访问已结束；后续 NR Evaluate、SR 和写回已获取的交换链图像可以留在 GPU 上执行。五个 timestamp 分别记录准备起止、评估起止、输出结束，输入 fence 的 CPU 空隙不计入 NR Evaluate GPU 时间。

SR 消费 NR ready semaphore，并向 SDK Present 传递独立的 SR ready semaphore。实际原生 Present 附带 maintenance1 fence，在当前线程的限定调用范围内允许先返回。下一次本链入口先等待上一 Present 退休，再完成 SR fence、读取 SR/NR GPU 查询并核对 NR fence；之后才复用命令池、查询池、信号量、参数与私有纹理。至多一个 pending slot，不同时运行两次 NR 历史评估。

SR 控制重建和 NR 尺寸重建发生在前一帧回收之后。外部交换链销毁、SDK 原生交换链销毁和设备关闭均先排空待退休呈现；不只依赖 `device_wait_idle` 来证明 Present 已退休。实际 FG 活动、NR-only、来源不足与读回帧保留同步路径。非成功的原生 Present 不启用延后。完成状态不明继续终止实验，不能复用在途资源。

新增 `route_present_submitted` 的单调 serial，与 `route_present_retired` 匹配。SR 提交记录 `fence_completed:false`，下一帧的 `target_sr_completion` 才记录真实完成；验收器要求 NR/SR 信号、帧号、fence、输出图像匹配，并拒绝越过第二次 Present 仍不回收、错误/重复完成、未排空即释放及不匹配的呈现退休。GPU 查询可能在下一帧日志中出现，不能仅按日志相邻位置认定它属于当前帧。

## 严格测试

`src-tauri/target/nr-tail-validation-001` 使用层 DLL SHA256 `44f667e60c5c464ecd89645d45a0d723bdcaf6ee74337d0955b386fb5eae8842`，固定模拟器、运行库 A、bridge、Streamline 2.12.0 和 VVL 沿用此前记录。

2,126 次 NR → DLAA 交接，最长 712 帧连续不重置；2,154 次应用呈现和原生退休匹配。6 次同步读回有限且无哨兵残留；前三次为加载画面，后三次为游戏中的强度 0.5，输入/输出平均差异约 0.00495，输出摘要变化。用户确认运动画面正常，明确未测试暂停；暂停、最小化、窗口 resize 未获实机验收。读回使用同步路径，异步画面由用户观察和完成证据补充，不声明正式画质通过。

初始验收器遗漏读取 `target_sr_completion`，因此错误报告 `submissions_fenced:false`。原报告保存为 `target-result-initial-reader-failure.json`；修正读取事件集合、补充读取路径回归后，对未修改的原始日志重新验收，NR 调用链与完成检查通过。层 DLL 未因该验收器修复改变。

进程正常退出码 0，NR/SR 与呈现清理完整。但仍有 **238 条验证错误、30 条未核查警告**，严格验收失败。相较紧邻前次严格会话出现 image-view-in-use 消息 `1672225264`，历史零 NR 评估基线 `nr-p1-native-001` 已有相同编号；本次也有 `vkQueueSubmit` 与 `vkDeviceWaitIdle` 之间的队列并发访问报错。历史出现不代表本次错误可以忽略或已定位到模拟器。完整编号、报告和原始文件摘要见 [summary.json](summary.json)。

## 检查与性能方法

119 个 Rust 测试通过、1 个专用硬件测试跳过。crate 的宿主/显式 Windows MSVC all-features/all-targets 检查、SDK-only、默认构建，以及主应用宿主/Windows 检查均无警告或错误；`cargo fmt` 通过。测试覆盖跨帧完成、借用输入前置完成、信号量匹配、重复/过期记录、退休平衡与待完成工作阻止销毁。

性能会话使用相同层 DLL、源 1920×1080、窗口 2560×1335、NR 强度 1、DLAA 100%、FG 关闭，相同计时和源跟踪设置，均为无验证层/无读回的 `--nr-performance`。`nr-tail-baseline-001` 设置 `NS_STREAMLINE_DEFER_PRESENT=0`，新路径会话设置 `1`。用户分别确认同一地点与视角，控制应用后预热三秒，串联采样 40 秒，全关参考 25 秒。平均 FPS 为完整连续帧间隔均值的倒数。分开进程的顺序采样不能替代确定性回放或长期统计。

该优化不减少 NR/SR 神经网络的计算量。链尾等待减少不等于整帧节省相同毫秒数，仍需检查等待是否转移到获取交换链图像或其他模拟器调度点。正式性能、画质、P1/P2 均未验收。

## 性能结果

| 区间 | 完整帧数 | 平均 FPS | 处理入口中位耗时 | 帧间隔 P95 |
| --- | ---: | ---: | ---: | ---: |
| 原链尾等待（已包含上一轮 GPU 中间交接） | 1,174 | 29.06 | 14.134 ms | 49.889 ms |
| 基线进程：全部关闭 | 756 | 30.00 | 0.714 ms | 33.787 ms |
| 延后链尾，第 1 次 | 1,207 | 29.90 | 3.889 ms | 37.092 ms |
| 新路径进程：全部关闭 | 756 | 30.00 | 0.678 ms | 37.017 ms |
| 延后链尾，再开启 | 1,203 | 29.81 | 3.880 ms | 36.942 ms |

平均帧率提高约 2.6%–2.9%，接近场景的 30 FPS；不能称为严格稳定 30 FPS 或外推至其他场景。渲染线程在处理入口的停留时长减少约 10.25 ms。新增前置输入提交/完成等待约 2.03–2.06 ms（包括上游 NVOF），下一帧的完整回收约 0.070–0.073 ms，原生 Present fence 本身约 0.003 ms。NR GPU Evaluate 仍约 8.14 ms，DLAA 约 2.81–2.86 ms，说明主要变化来自允许 CPU/GPU 工作重叠。hook 外间隔也增加，不能把入口减少的 10 ms 全算成整帧提速。

跨帧 GPU 查询按原始提交归属统计：NR 对应尚待完成的 NR 提交，SR 用明确的 frame ID 匹配，避免把下一帧才读取的结果错误计入当前帧。CPU 回收等待仍归入实际执行等待的帧。

新性能进程完成 5,242 次延后 NR/SR 交接，6,170 次原生 Present 提交/退休一一匹配，最长连续 2,220 帧不重置。两次串联区间之间覆盖全关和重新开启，用户确认画面正常。三个测试进程均正常退出，最终无未完成呈现；无验证层会话只有调用链完成证据，不具有严格输出/验证验收资格。

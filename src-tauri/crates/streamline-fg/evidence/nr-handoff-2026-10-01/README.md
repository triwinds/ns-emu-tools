# NR → DLAA GPU 交接实验（2026-10-01）

实现了 NR 提交后继续录制、提交 DLAA，由 GPU semaphore 保证交接顺序，保留 SR 链尾 fence 等待。此改动只覆盖原生 NR 实验内部，P1/P2 与严格验证仍未通过。统计与原始证据摘要见 [summary.json](summary.json)。

## 同步与生命周期

NR 提交等待上游 NVOF 信号并发出独立的二进制 `ready` semaphore；SR 只消费这个信号，不重复消费游戏/NVOF 信号。SR fence 完成后，以非阻塞 `get_fence_status` 核对同队列的 NR fence，之后才允许复用命令池、查询池、feature 参数及输出纹理。NR 私有输出到 SR 的图像转换保留。

资源复用仍限于一帧处理链。NR 单独运行以及实际读回帧保持原来的 CPU 等待；读回结束后恢复 GPU 交接。尚未完成 NR 提交时拒绝下一次运行，完成状态不明时继续沿用终止实验的策略，不向游戏返回可能未完成的输出。没有删除链尾同步、增加在途帧数或调整神经网络算法。

`NS_STREAMLINE_NR_GPU_HANDOFF=0` 恢复旧等待路径；未设置或设为 `1` 时，非读回的 NR → SR 使用新路径。两个无验证层性能进程使用相同的新构建，仅该环境开关不同。层 DLL SHA256：`6f034127be986a55195ab180faa2c78ac3e881f203d42ea689b818f3c1c779d6`。

`target_nr_submission` 如实记录尚未完成的 fence 与待消费 semaphore，`target_sr_frame` 记录实际消费的信号以及链尾 fence 完成，`target_nr_completion` 随后记录 NR fence 检查成功。验收器要求三者在本帧内按顺序匹配，不接受缺失/重复/错配/早于 SR 或晚于 Present 的完成记录。旧的同步日志仍可验收。NR GPU 查询延后至 SR 完成读取，不增加 query WAIT。

## 严格验证

会话 `src-tauri/target/nr-handoff-validation-001`：1,753 次 NR → DLAA 交接，最长连续 801 帧不重置历史。6 次读回均有限、无哨兵残留；前三次是加载画面，后三次为用户进入游戏后强度 0.5 的样本，输入/输出平均差异约 0.0052，输出摘要随帧变化。读回帧使用同步路径，不能单凭这些读回证明异步路径画质。用户另外确认 GPU 交接运行时运动画面正常。

进程退出码 0，NR 与 SDK 清理完整，交接与完成证据通过。但仍有 **220 条验证错误、30 条未核查警告**，严格验收失败。相较 `nr-history-validation-002` 新出现消息编号 `-1604639890`：GUI.RenderThread 提交 fence 时 GPU.MainThread 同时等待该 fence。历史 `nr-p1-native-001`（NR 实际评估 0 次）已出现相反报告顺序的同类跨线程 fence 消息，编号 `1010413496`。这不能证明本次消息一定与优化无关；消息没有对象句柄，具体归因仍未解决。其余已发出错误编号见 summary；不屏蔽错误或将其自动归因于模拟器。

## 性能方法

固定模拟器、运行库 A、Streamline 2.12.0、RTX 5070 Ti Laptop 与驱动沿用上一轮。源 1920×1080、窗口 2560×1335、NR 强度 1、DLAA 100%、实际 FG 关闭。两轮均显式 `--nr-performance`，不加载验证层、不读回，保留相同的源跟踪和 CPU/GPU 计时。用户分别确认同一地点、同一视角。

旧路径会话 `nr-handoff-baseline-001`；新路径会话 `nr-handoff-performance-001`。控制应用后等待三秒，串联区间各 40 秒，全关区间各 25 秒。新路径额外全关后再开启采样一次。平均 FPS 使用完整连续帧间隔均值的倒数；不以局部 NR wait 变成零宣称性能提高。GPU 算法耗时仍存在，SR fence 等待会包含上游 NR。

| 路径 | 完整帧数 | 平均 FPS | Present hook 中位数 | NR CPU 等待中位数 | SR CPU 等待中位数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 旧 CPU 等待 | 1,077 | 26.70 | 14.539 ms | 9.752 ms | 2.842 ms |
| 旧路径进程：全关 | 757 | 30.00 | 0.699 ms | — | — |
| 新 GPU 交接，第 1 次 | 1,150 | 28.47 | 14.025 ms | 0 ms | 12.210 ms |
| 新路径进程：全关 | 756 | 30.00 | 0.638 ms | — | — |
| 新 GPU 交接，再开启 | 1,187 | 29.42 | 14.187 ms | 0 ms | 12.358 ms |

本轮观察到平均 FPS 提高约 6.6%–10.2%，但仍非稳定 30 FPS。hook 中位数实际只减少约 0.35–0.51 ms；NR 的 GPU Evaluate 仍约 8 ms，DLAA 约 2.6–2.8 ms。大部分等待移到了 SR 链尾，不能把原 NR wait 的 9.75 ms 当成节省量。两轮为独立进程、顺序采样，没有确定性回放；不能将全部 FPS 差异精确归因于减少的 CPU 间隙，也不外推至所有场景。外部游戏调度/呈现节奏和链尾阻塞仍需后续定位。

新性能进程完成 4,902 次异步交接，最长连续 2,095 帧不重置；关闭再开启后继续通过完成与交接检查。两个性能进程均未加载验证层，均正常退出且清理完整；严格进程实际有 1,747 次异步交接及 6 次同步读回交接。三个会话的严格/正式验收标记均保持失败或未验收。

## 构建检查

Rust 全 feature/target 回归测试通过，新增完成证据测试拒绝错误的输出/信号量、未完成 SR、提前完成、重复完成及 Present 前未退休的提交。`cargo fmt`、crate 宿主与显式 Windows MSVC all-features/all-targets 检查、SDK-only 与默认构建检查，以及主应用宿主/Windows 检查均无错误或警告。Release 使用 `--features native-nr --lib --bin streamline-layer-probe`。

本轮只实施中间交接优化。跨帧并行、最终 CPU fence 延后、格式转换和拷贝优化仍未实现；正式性能、画质、P1/P2 标记保持 false。
